# CoupLB Developer Notes: 2026-07-02 Pre-release Review

This note documents the bugs found in the pre-announcement review, the
root-cause analysis of the most serious one, why the existing test suite
did not catch any of them, and the lessons we are codifying. Companion
records: `CHANGELOG.md` (what changed), `tests/run_continuation/` (the new
regression gate).

---

## Fixed Issues (summary)

1. **Fluid state silently reset at every `run` command boundary** (HIGH) —
   root-caused below.
2. `setup()` double-applied the previous run's final IBM force spread on
   continuation.
3. Stability check was NaN-blind: a corrupted field reported `Ma=0.0000`
   because max-reductions skip NaN (all comparisons with NaN are false).
   Mass/momentum sums *do* propagate NaN, so the check now traps
   non-finite diagnostics with a hard error.
4. `xi_ibm <= 1` validation rejected the shipped `examples/swimming` deck
   (`xi_ibm 5`, `md_per_lb 167`). The stability-relevant quantity is the
   per-substep relaxation ξ/N, so the bound is now `0 < xi_ibm <= md_per_lb`.
5. Both examples aborted at step 0 in a fresh clone: they write to a `vtk/`
   directory that git cannot track while empty. Decks now run
   `shell mkdir -p vtk`.
6. README build instructions were incomplete: COUPLB must be *registered*
   in `cmake/CMakeLists.txt` (`STANDARD_PACKAGES`) or `src/Makefile`
   (`PACKAGE`) before `-DPKG_COUPLB=yes` / `make yes-couplb` does anything.
   With CMake the unregistered flag is **silently ignored** — the build
   succeeds and the failure surfaces later as "Unknown fix style".

## Root Cause: Why the Fluid Reset Happened

The bug was not a typo — it was a correct-looking design decision built on
a wrong assumption about the host framework's lifecycle. The chain:

### 1. LAMMPS `init()` is per-run, not per-fix

LAMMPS calls `Fix::init()` at the start of **every** `run` command. Its
intended role is *re-validation and re-derivation*: the user may have
changed `timestep`, added fixes, or altered neighbor settings between
runs, so every fix gets a chance to refresh derived quantities. The
natural mental model when writing a new fix — "`init()` initializes, once"
— is exactly wrong. It is a *refresh* hook, not a constructor.

### 2. The grid setup genuinely needed init-time information

`setup_grid()` sizes the local lattice from the domain decomposition and
derives τ and the unit scales from `update->dt`. Putting that logic in
`init()` was reasonable — parts of it (τ, scales) *must* re-run per run.
The error was granularity: one function conflated

- **parameter refresh** (cheap, must repeat every run), and
- **state creation** (`allocate` + `init_equilibrium`, must happen once),

and executed both unconditionally. Every `run` boundary therefore rebuilt
the lattice and set it to quiescent equilibrium.

### 3. CoupLB is unusual among fixes: it owns primary state

Most LAMMPS fixes hold *derived* state that can be recomputed from the
atom data at any time — for them, rebuild-on-init is idiomatic and safe.
CoupLB's distribution functions are *primary* physical state with no
atom-side backup: rebuilding is destroying. The same trap would not bite a
thermostat; it bites any fix that embeds a field solver. (LAMMPS's own
LATBOLTZ `fix lb/fluid` allocates its fluid arrays in the **constructor**
and uses `init()` only for parameter re-derivation — the idiom we now
follow in spirit, with an idempotence guard instead, so that decomposition
changes are still detected.)

### 4. A standalone-solver habit, embedded

A standalone LB code runs `allocate → init_equilibrium → time loop` once
per process, and that structure is correct there. Embedding the same
structure into a host with a re-entrant lifecycle silently changed its
meaning. When code moves into a plugin/callback framework, every "runs
once" assumption must be re-checked against the host's actual contract.

### The fix

`setup_grid()` now compares the required local dimensions, offsets, and
`dt_LBM` against the existing grid. Unchanged → preserve the fluid, refresh
τ only. Changed → reallocate (as before) with a loud `CoupLB WARNING` that
the fluid was reset. `run N; run M` is now bit-identical to `run N+M`.

## Why the Test Suite Missed It

The bug existed from the first version of the current architecture and
survived two prior code reviews (2026-04-29, 2026-05-30) plus a validated
paper. Four independent masks stacked:

1. **Every shipped test uses exactly one `run` per LAMMPS invocation.**
   The reset path only executes on the *second* `run` of a session; the
   first `init()` finds no grid and allocates legitimately. Coverage was
   structurally impossible.
2. **The multi-phase workflow used the one immune pattern.** The
   subcycling test chains phases as *separate LAMMPS invocations* connected
   by `checkpoint`/`restart` files. State comes from disk; each process has
   a single `run`. The cluster-style workflow accidentally sidestepped what
   a plain `run 5000; run 5000` script hits immediately.
3. **Steady-state observables self-heal.** Everything validated
   quantitatively (Poiseuille/Couette profiles, terminal drag velocity) is
   a steady state checked against an analytic solution. A mid-run reset
   only delays convergence toward the *same* answer — run long enough and
   the test passes anyway. Only a transient or history-dependent quantity
   measured *across* a run boundary can expose the bug, and no test
   measured one.
4. **The one affected deck could not testify.** `examples/swimming` has
   three `run` commands, so its fluid *was* being wiped — but its output is
   a qualitative steady gait (looks fine after re-development), and since
   the 2026-05-31 `xi_ibm` cap it errored at startup, so it was not being
   re-run at all.

## Lessons Learned

**L1 — Host lifecycle hooks are re-entrant; state creation must be
idempotent.** In a plugin framework, learn what the host actually promises
about each hook (`init()` = per-run refresh in LAMMPS) before deciding what
lives there. Separate "refresh derived parameters" from "create state",
and guard state creation so re-entry preserves it.

**L2 — Outcome tests cannot see state-handoff bugs; differential
invariants can.** Validating steady states against analytic solutions
proves the physics of a single uninterrupted run and nothing else. The
gates that catch seam bugs are equalities the implementation must satisfy
*exactly*: `run N; run M == run N+M`, restart == uninterrupted,
1 rank == N ranks. The run-split check found in minutes what analytic
validation missed for the project's lifetime. It is now a permanent test
(`tests/run_continuation/`).

**L3 — Re-run every shipped example after tightening input validation.**
The `xi_ibm <= 1` cap (added 2026-05-31) broke `examples/swimming`
(written 2026-04-27) and nobody noticed because examples are not in the
test loop. A validation gate that rejects a shipped artifact means either
the gate or the artifact is wrong — resolve the conflict when it appears;
do not let it stand. (Here the gate was wrong: it capped ξ instead of the
per-substep ξ/N.)

**L4 — First-contact paths need a clean-room test.** Build instructions
and example step 0 were both broken for a fresh user (unregistered
package flag silently ignored; missing `vtk/` directory) while working
perfectly on developer machines, because developer trees carried uncommitted
fixes (the CMake registration, the created directory). Before announcing:
fresh clone, vanilla upstream LAMMPS, follow the README verbatim, run every
example.

**L5 — Max-reductions are NaN-blind; sums are not.** Any "max |u| sanity
check" silently passes a fully corrupted field because NaN comparisons are
false. Pair max-based checks with a summed quantity plus `isfinite`, which
NaN poisons reliably. This generalizes to any reduction-based health
monitor.

**L6 — "All tests green" measures the suite, not the code.** Two thorough
line-by-line reviews (32 findings) missed the highest-severity bug because
review reads code paths, and this path only exists across two `run`
commands. Reviews and outcome tests must be complemented by adversarial
*use* — exercising the workflows users actually run (multi-run scripts,
fresh installs) rather than the workflows tests were written for.
